# Brief for a cloud Claude session: the Crash Sandbox video pipeline

You're helping **toyfantv**, a music producer who also makes Roblox videos (Shorts / TikTok / YouTube):
car crashes, anime characters (Uma Musume, Goku...), slapstick, fights. Their videos are staged in
**Crash Sandbox**: a Roblox place built entirely from code, on their Windows PC, with Roblox Studio,
OBS and a local Claude Code session that drives Studio over MCP.

**Your job:** research, then design and write the scripts that run the whole cycle in one go:
**scene → recording → post-production edits**. One take should produce several finished cuts:
a plain cut, an anime-style cut (impact frames, face panels, speed lines...), a cinematic cut, in
16:9 and vertical. Write code the user can carry back to their PC; the local session integrates and
tests it against Roblox Studio.

---

## 1. Who runs what (hard constraints)

| | Cloud session (you) | Local PC (the user + local Claude Code) |
|---|---|---|
| Roblox Studio, its MCP server, OBS | **no** | yes (Windows 11) |
| Edit Lua scenes / game code | yes (text) | yes, and play-tests them |
| Record a take | **no** | `python tools/record.py ...` |
| ffmpeg / Python video processing | yes: develop and test on the sample videos | yes: runs the final pipeline |
| GPU encoding | probably not | NVIDIA: `h264_nvenc` (fall back to `libx264` when it's missing) |

So: build and test the **post-production half** fully on the sample videos and timelines in this
bundle. For the **game half** (exporting a timeline, re-rendering a take from other cameras), write
a precise spec and draft code. The local session wires it in, because only it can run Studio. Mark
anything you couldn't run as untested.

Target environment: Windows, Python 3.11, ffmpeg 6+ on PATH, `pip`-installable packages only
(numpy, opencv-python, Pillow, PyYAML are fine; avoid heavy ML models unless clearly optional).
Use `pathlib` paths and `subprocess` lists, no bash-isms. Text files use LF line endings and UTF-8.

## 2. The project in one page

Repo: `D:\Claude\crash-sandbox` (git). Luau code is generated into a `.rbxlx` place by `build.py`
(no Rojo). Read `README.md`, `SCENES.md` (the scene format: a big reference) and `HANDOFF.md` from
this bundle.

- **Scenes** are data: `scenes/<collection>/<name>.lua` returns a table: `map` (location), `lighting`,
  `colorMode`, `vehicles` (scripted driving, `aimAt`, `afterHit`), `characters` (avatars, the saved
  `cast`, `actions` queues: walk, sit, punch, shoot, bazooka, leap, forceStop, slip...), `dialogue`
  (speech bubbles, lip sync), `cameras` and a `shots` list (scripted cuts) or a `director` (automatic
  cutting: `story`, `cinematic`, `coverage`, `dramatic`). Times are **seconds after GO**.
  Examples in this bundle: `stories/haru_bike.lua` (the newest: scripted shot list),
  `stories/crosswalk_bus.lua`, `people/office_slapstick.lua`.
- **Runtime**: `src/server/CrashServer.server.lua` loads a scene, runs the countdown and the action;
  `src/server/modules/*` (vehicles, damage, characters, acting, weapons, faces, effects);
  `src/client/CrashClient.client.lua` is the camera system: directors, shot types (`fixed`, `chase`,
  `onboard`, `closeup`, `track`, `beat`...), speech bubbles, lip sync, and a **replay buffer** (below).
- **The cast**: `src/shared/Cast.lua` (generated by `tools/cast.py`): saved characters with
  everything they wear (goku, haru_urara, oguri_cap). Every new character gets saved there.
- **Tools** (all Python, run on the PC): `tools/sync.py` (push scripts into the open place),
  `tools/shoot.py` (play + timed screenshots), `tools/record.py` (record a take),
  `tools/studio_mcp.py` (tiny MCP client: `lua <Server|Client|Edit> -e "<code>"`), `tools/cast.py`,
  `tools/scene_index.py` (where scenes live), `tools/tidy.py`.

### Recording today (`tools/record.py`, in this bundle)
`python tools/record.py <scene> --obs --seconds 15`:
1. puts Studio in Play, loads the scene (frozen setup mode), waits for the client's preload, hides
   all UI, turns the replay buffer off unless needed;
2. records the 3D view with OBS (own profile; **Roblox Studio's audio only**), 60 fps;
3. presses start, waits, stops; **cuts the raw file to start exactly at GO** (wall-clock estimate
   snapped to the director's camera cut at GO) and lasts `--seconds`;
4. default `--format both`: `recordings/<scene>_<YYYYmmdd_HHMMSS>.mp4` = **1920x1080 16:9** (the
   sides of Studio's ~2.6:1 view cropped) **plus** `..._4x5.mp4` = **1080x1350** vertical, the centre
   4:5 slice of the same take. Cameras compose so the action and speech bubbles stay inside that
   centre slice;
5. optional: `--smooth` (motion-interpolate dropped frames), a scene's `introAudio` (a local mp3
   mixed in from frame 0).

Files: H.264 yuv420p 60 fps, AAC 48 kHz stereo, ~3 MB/s. **t = 0 in the video = GO in the scene.**
The 3D view is only ~690 px tall on their screen, so the output is upscaled: keep that in mind for
crops (a face panel cropped from a wide shot is very soft: see §4).

### Limits worth knowing
- **Physics isn't deterministic.** Recording the same scene twice gives a different crash. You can't
  get "the same moment from another angle" by re-recording.
- **But there's a replay buffer.** The client samples every moving part's CFrame (vehicles, debris,
  characters as puppets) at 30 Hz for `scene.replaySeconds` (default 14) and can replay it at any
  speed, from any camera (key T; `startReplay({from, to, once})` in CrashClient). Particles, sparks,
  smoke, faces and bubbles aren't in the replay; character puppets are rigid copies. This is the way
  to get extra camera passes (ISOs) of the exact same take: see §3B.
- Frame rate dips during huge crashes (to ~20 fps for ~2 s). OBS records at 60, so those moments show
  repeated frames; `--smooth` interpolates them.
- Audio: the game's own funny SFX pack (screams, bonks, horns, booms, a laugh track). No music; the
  user is a music producer and may add their own.

## 3. What to build

### A. A take timeline (game side: spec + draft; local session implements)
The edits need to know **what happens when, and where on screen**. Today only fragments exist
(`DirectorLog` = camera cuts, `SfxLog`, server "beat" events: who speaks / hits / shoots, impacts).
Define a JSON sidecar written next to every recording, `<video>.timeline.json`. Proposed shape (refine
it, it's your design):

```json
{
  "scene": "haru_bike", "title": "Learning to Ride", "fps": 60, "duration": 14.8,
  "video": { "wide": "haru_bike_..mp4", "vertical": "haru_bike_.._4x5.mp4", "verticalCropX": [420, 1500] },
  "cuts":     [ { "t": 1.92, "camera": "low car", "type": "chase" } ],
  "dialogue": [ { "t": 0.3, "dur": 2.0, "who": "haru", "text": "Okay, okay... nice and steady...", "face": "nervous" } ],
  "events":   [ { "t": 4.62, "kind": "power", "who": "goku", "target": "car" },
                { "t": 9.86, "kind": "impact", "who": "bus", "target": "haru", "speed": 150, "pos": [46, 3, 6.5] },
                { "t": 9.86, "kind": "knock", "who": "haru" } ],
  "sounds":   [ { "t": 9.86, "cat": "scream" } ],
  "tracks":   { "haru": [ { "t": 9.0, "head": [0.62, 0.41], "box": [0.55, 0.30, 0.70, 0.62], "onScreen": true } ] }
}
```
`tracks` = per-character normalised screen positions (head point + body box), sampled ~15-30 Hz on the
client with `Camera:WorldToViewportPoint` (mapped to the 16:9 crop). It drives auto-reframing, face
panels, captions next to speakers, and punch-in zooms. Server events come from the existing beat
system (`ctx.beat(...)`, `Damage` impacts, `NPC:knock`, `Sfx.play`) and need timestamps relative
to GO.

A **hand-made fixture** for the sample take is in `samples/haru_bike_20261004_174731.timeline.json`.
It's built from the scene script plus scene-change detection on the video. Use it to develop and
test, and treat it as approximate.

### B. Extra camera passes from the replay (game side: spec + draft)
For face panels and close inserts that aren't soft upscaled crops: after the main take, re-render
parts of the **same take** through the replay buffer from other cameras (e.g. a face close-up of
each character at each impact), recorded as separate clips with their own sidecars ("ISO passes").
Specify: which windows and cameras to render (derived from the timeline: impacts, dialogue), how
record.py drives it (`CrashCam` / `CrashReplay` player attributes, `startReplay`), and the limits
(rigid puppets, no particles: fine for inserts held 0.3-1.0 s).

### C. The editor (post-production: build and test fully)
`tools/edit/` (a package) + `tools/produce.py` (the orchestrator). Inputs: a recording (+ 4:5
companion), its timeline, optional ISO clips, a **cut recipe**. Output: finished MP4s per recipe and
aspect (16:9 and vertical; for vertical, prefer re-framing the 16:9 master with the tracks over a
fixed centre crop; 9:16 is fine when the reframe stays sharp enough).

**Recipes** are data (YAML/JSON) so new styles don't need code: a list of rules keyed on timeline
events, e.g. "on every `impact`: hit-stop 4 frames, impact-frame flash 3 frames, shake 10 frames,
SFX `boom`"; "on dialogue: caption the line near the speaker"; "at the climax: speed ramp to 0.4x
for 1.5 s". Ship at least:
- **plain**: the take as is, plus captions (optional), loudness-normalised;
- **anime**: impact frames (2-4 frames: inverted / posterized / high-contrast monochrome with
  radial speed lines, then back), hit-stop (freeze 3-6 frames on contact), screen shake, radial blur
  or speed lines on fast action, manga-style **face panels** (split the frame into slanted panels
  with the characters' reaction close-ups, from ISO passes or tracked crops, with white gutters and
  a quick slide-in), a "character intro" freeze card (name label) when someone first appears, onomatopoeia
  text ("BAM!", "KABOOM!") at impacts, a short zoom punch-in on the reaction;
- **cinematic**: speed ramps around the big moment (slow-mo via frame interpolation, then snap back),
  a slow push-in on dialogue close-ups, a subtle color grade (no vignette, no letterbox bars: see
  preferences), an L-cut / J-cut of the SFX across cuts, a clean title card;
- **shorts**: vertical, fast pacing (trim dead air between events), big captions, a hook in the first
  second (start on, or flash-forward to, the climax), loop-friendly ending.

Implementation hints (verify with your own research): ffmpeg filter graphs for cutting, speed
(`setpts`, `minterpolate` for slow-mo), zoom (`zoompan`/`scale`+`crop` with expressions), overlays;
OpenCV / numpy for per-frame effects (impact frames, speed lines, panel compositing); Pillow for
text and panels. Keep the audio in sync through every time remap (hit-stop and slow-mo need matching
audio handling: stretch, cut, or bridge with an SFX). Render through an intermediate image sequence
only where needed. Each recipe should render a 15 s 1080p take in a reasonable time on a PC (well
under 5 minutes).

### D. The orchestrator
`python tools/produce.py <scene> [--recipes anime,cinematic,shorts] [--takes 2]` on the PC:
1. `tools/sync.py --scene <scene>` (or build), play-test hook optional;
2. `tools/record.py <scene> --obs ...` (writes the take + timeline); optionally several takes, and
   keep the best (e.g. the one whose timeline has the expected key events: the impact happened,
   characters on screen at the climax);
3. ISO passes from the replay (when implemented);
4. render every recipe × aspect into `recordings/<scene>/<take>/<recipe>_<aspect>.mp4` plus a
   contact sheet (thumbnails), so the user can compare cuts quickly;
5. print a summary. Every step resumable on its own (`--from edit`).

## 4. The user's preferences (follow them)
- Formats: **horizontal is 16:9** (cropping the sides of the wider view is fine); **always compose
  for vertical too** (4:5 is OK; it doesn't have to be a full 9:16).
- **No vignette and no letterbox bars.** They asked for those to be removed.
- Bright, vibrant colour (the `vibrant` colour mode), faint bloom.
- Comedy matters: timing beats (setup, a calm beat, then the gag), funny SFX, the laugh track
  option. Cinematic but readable camera work. They like seeing results: contact sheets, stills.
- Video starts at the action (no countdown / static pre-roll).

## 5. What to hand back
1. `tools/edit/` + `tools/produce.py` + recipes (`tools/edit/recipes/*.yaml`) + a README section, all
   tested on the sample videos (include the rendered sample outputs or contact sheets as proof).
2. The **timeline sidecar spec** (final JSON schema) and the **ISO-pass spec**, with draft Lua / Python
   for the game side (client sampling of tracks, server event log, record.py changes) clearly marked
   untested.
3. A short list of open questions / choices for the user.
Keep changes to existing files minimal and describe them; the local session merges and tests in Studio.
